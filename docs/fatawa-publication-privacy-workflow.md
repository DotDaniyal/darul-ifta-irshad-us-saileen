# Controlled Public Fatwa Publication Workflow

## Purpose

This procedure is the required release gate for every new or replaced public Fatwa PDF. It preserves the substantive Fatwa question, answer, Islamic references, official record details, and approved Darul Ifta contact information while preventing public disclosure of question-submitter names, private phone/mobile numbers, addresses, signatures, case attachments, and similar direct identifiers.

> **Fail closed:** a raw source PDF must never be linked from the public catalog. If the audit is incomplete, malformed, uncertain, or visually unverified, the document remains unpublished until a scholar or designated reviewer records a conservative manual resolution.

## Approved information boundary

| Keep in the public derivative | Remove or exclude from the public derivative |
| --- | --- |
| Substantive question, Fatwa answer, Islamic references, case reasoning, Fatwa number, issued-record details, institutional seals, and official Darul Ifta contact information | Question-submitter names, private numbers, addresses, personal records, signatures, contact blocks, and privacy-dense supporting attachments |

The approved institutional contact is `0332617671`. The existing institutional footer formats `03332617671` and `+92 333 2617671` are also retained when they clearly identify Darul Ifta. Any other phone or mobile number is treated as private unless a reviewer documents an institutional basis for retaining it.

## Required release sequence

| Stage | Required action | Release gate |
| --- | --- | --- |
| 1. Stage | Keep raw PDFs and raster review files outside the project source tree. Do not commit or catalog-link them. | Confirm source inventory and unique archive slug. |
| 2. Audit | Build the source manifest and run the visual audit. Record direct identifier regions per page. | Resolve every audit error or malformed response through conservative manual review. |
| 3. Build | Generate the fail-closed public-redaction manifest. Add manual masks or page exclusions where needed. | The manifest must cover every catalog record. |
| 4. Render | Raster-render the selected pages, apply masks, and rebuild an image-only public PDF. | Confirm readable PDF output and selected page count. |
| 5. Review | Visually inspect the identity/contact zones at readable scale and representative pages of the derivative. | Verify that direct identifiers are gone and substantive Fatwa content remains readable. |
| 6. Publish | Upload the verified derivative to a fresh managed storage path, update `scripts/fatwa-public-sanitized-url-manifest.json`, and regenerate `client/src/data/fatawa.ts`. | Never reuse a raw source URL or rely on an overwrite of an existing raw asset. |
| 7. Validate | Run the privacy routing regression and the full application release checks. | Catalog count, sanitized-manifest count, and unique public URL count must agree. |

## Project safeguards

The public catalog is generated by `scripts/generate-fatawa-catalog.mjs`. It rejects a catalog build unless the sanitized URL manifest has one entry for every archive record, and it emits only managed `sanitized-fatwa-…` paths. `client/src/data/fatawaPublicPrivacy.test.ts` verifies that public viewer, preview, download, and search routes resolve only to those sanitized paths. `client/src/data/fatawaSanitizedManifest.test.ts` verifies that the manifest is complete and matches the generated catalog exactly.

Use `scripts/build-fatwa-public-redaction-manifest.mjs` and `scripts/render_sanitized_fatawa.py` for the existing release pipeline. Keep temporary manifests, audits, review images, and upload logs out of the committed project tree after the release evidence has been recorded. The site does not provide a staff self-upload portal; publication remains a controlled reviewer-led process.

## Replacement and incident rule

If a post-publication review finds a direct identifier, immediately remove the record from catalog generation or point it to a corrected fresh sanitized derivative, then rebuild, retest, and publish. Previous raw storage URLs must not be catalog-linked. Because a previously shared direct URL can have an independent cache lifetime, do not claim its external revocation without verified storage-platform invalidation.
